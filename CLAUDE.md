# imetrobert.github.io — content editing guide

Static personal site + AI-generated blog (custom domain `www.imetrobert.com`,
served via GitHub Pages, `.nojekyll`). Two very different content surfaces —
read the right section below before editing.

> This file is deliberately short (it loads every session). Detailed rules live in
> `docs/` and are read on demand: `docs/blog-pipeline.md` (blog generation, approval page,
> sourcing, dates, sharing) and `docs/site-rules.md` (SEO/AEO, never-index rules, icons,
> brand mark). Use `grep -n '^##' docs/<file>` to find the section, then read only that range.
> Scripts are big (`generate-preview-page.py` 101KB, `renderer.py` 80KB, `gemini.py` 61KB,
> `parser.py` 47KB, `utils.py` 43KB, `blog_index.py` 37KB): grep for the function, never read
> a whole file.

## `index.html` — the homepage (hand-edited)

This is the only file on the site meant to be edited by hand. All CSS now
lives in `css/style.css` (extracted from three inline `<style>` blocks that
used to make up ~62% of the file — pure formatting move, no visual change).
**Edit `css/style.css` for styling, `index.html` for content — you should
almost never need to touch both for a content change.**

## `blog/` — generated, never hand-edit

Posts are generated by a monthly GitHub Action (Gemini), staged, previewed, and published
to `blog/posts/` only after Approve. Generated and overwritten on each publish:
`blog/posts/*.html`, `blog/posts/latest.html`, `blog/index.html`, `sitemap.xml`, `feed.xml`,
`llms.txt`. Voice or section changes are prompt/code changes in `scripts/`, not post edits.

Non-negotiables (full reasoning in `docs/blog-pipeline.md`):

- Section contract is three files: `gemini.py` (emits) → `parser.py` (splits) → `renderer.py`
  (renders). Add/rename/remove a section in all three, or it vanishes silently.
- Run scripts from the repo root (`python3 scripts/xxx.py`), never `cd scripts`.
- CSS classes `.roberts-take`, `.roberts-header`, `.roberts-body` are load-bearing for
  `inject_take.py`; do not rename them.
- Monthly generation must be search-grounded; no silent ungrounded retry. Only PROVEN models
  may lead: the baseline (`gemini-2.5-flash`, `-flash-lite`, `gemini-2.0-flash`) plus whatever
  `scripts/model_scout.py` has qualified in `blog/model-config.json` (weekly `model-scout.yml`,
  or "Test for new models now" on the preview page). Best proven model leads automatically;
  "Pin" on the preview page overrides. Never make an unproven model lead.
- Never index `/blog/staging/` (robots.txt Disallow AND `noindex` meta on every page there).
- Share links always use the post permalink, never `latest.html`.
- No emoji on visitor-facing pages (inline SVG icon sprite instead).
- `git rm`-ing a published post is not enough: it stays in the sitemap and index unless turned
  into a redirect stub (noindex + meta-refresh).
- Workflows are `workflow_dispatch` (fired from the preview page) except `monthly-blog.yml`
  (daily 09:00 UTC, generates on the last day of the month) and `keepalive.yml`.
  `redraft-section.yml`'s section choice list is hand-maintained.

Since the December 2026 issue the briefing is written for small Canadian businesses (what the
low-cost AI plans can do) and ends with one feasibility-check call to action. Section headers in
the text are unchanged; page titles and prompt meaning changed. Read "Audience and focus since
the December 2026 issue" at the top of `docs/blog-pipeline.md` before touching the prompt.

Sections in `docs/blog-pipeline.md`:

- Dates — nothing may be reported before it happens
- Brand — one definition in `utils.py`
- Sharing — always the permalink, never `latest.html`

## Editing without Claude Code (plain claude.ai chat, no repo access)

Same approach as other repos in this account:

1. Find the section via the id table above (`grep -n 'id="SECTION"'
   index.html` on GitHub, or Ctrl+F in the GitHub file view).
2. Copy just that `<section>...</section>` block (or the specific line for
   a fact like the phone number) into chat with your requested change.
3. Paste the result back via GitHub's web editor.
4. If it's a repeated fact (see checklist above), repeat per location —
   small individual pastes, not the whole file.
5. Never paste all of `css/style.css` for a content question — styling and
   content are separate files precisely so you don't have to.
